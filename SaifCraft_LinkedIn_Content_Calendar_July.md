## Day 8 — 3 JWT Mistakes That Will Eventually Get Your App Breached

**Format:** Technical How-to / Warning

**Post:**

JSON Web Tokens are everywhere. And they're being misused everywhere.

Here are the three mistakes I see most often when auditing client codebases — and exactly how to fix them:

**Mistake 1: Storing JWTs in localStorage**
localStorage is accessible by any JavaScript on your page — including injected scripts from XSS attacks. Store access tokens in memory and refresh tokens in `HttpOnly` cookies instead.

**Mistake 2: Not validating the algorithm (RS256 vs HS256 confusion)**
An attacker can modify a JWT header to switch from RS256 to HS256, then sign the token with your *public key*. If your server doesn't validate the algorithm before verifying, it will accept forged tokens.
Always explicitly specify and enforce the expected algorithm server-side.

**Mistake 3: Tokens that never expire (or never get rotated)**
A stolen token with no expiry is a permanent key. Use short-lived access tokens (15 minutes), implement refresh token rotation, and invalidate tokens on logout — not just on the client side.

These aren't advanced security concepts. They're table stakes for any SaaS product that handles user data.

Security isn't a feature you add before launch. It's a practice you build into every PR.

**Where I'd still be cautious:**
→ Complex enterprise apps with deep dependency trees (compatibility edge cases remain)
→ Applications where you need maximum ecosystem maturity

My current approach: use Bun for development tooling and new greenfield edge functions. Keep Node.js for established production API services until the ecosystem matures further.

## Day 14 — How to Write a Developer Brief That Actually Gets You What You Want

**Format:** How-to / Advice for Founders

**Post:**

The single biggest cause of "this isn't what I asked for" isn't a bad developer.

It's a bad brief.

After reviewing hundreds of project inquiries, here's what separates the briefs that produce great results from the ones that produce expensive misunderstandings:

**Include: What problem does this solve for which user?**
Not "I need a dashboard." → "I need our logistics managers to see real-time shipment status so they stop calling our support team 40 times a day."

**Include: What does success look like in 90 days?**
A metric is worth a thousand feature descriptions. "Users should be able to complete onboarding in under 3 minutes" is more useful than "make it user-friendly."

**Include: What already exists (if anything)?**
Existing Figma designs, brand guidelines, a backend API, a database schema — anything that constrains or accelerates the build.

**Include: What's out of scope (for now)?**
The features you're deliberately deferring are just as important as the ones you're building. Writing them down prevents "while we're at it..." conversations mid-project.

**Omit: Specific technology choices (unless you have strong technical reasons)**
Let the developer recommend the stack. Your job is to define the outcome, not prescribe the implementation.

A clear brief is a professional courtesy. It saves time, reduces cost, and produces better software.

If you're working on a project right now — does your brief pass this test?

## Day 16 — PKCE Is Now Mandatory. Is Your OAuth Implementation Up to Date?

**Format:** Technical Insight / Industry Update

**Post:**

In January 2025, the IETF published RFC 9700 — the OAuth 2.0 Security Best Current Practice.

It makes two changes every developer building with OAuth should know:

**1. The Implicit Grant flow is officially deprecated.**
If your app is using `response_type=token` in an OAuth flow to get an access token directly from the authorization endpoint — stop. This flow leaks tokens in browser history and referrer headers. It's gone.

**2. PKCE is now mandatory for all client types — including confidential clients.**
PKCE (Proof Key for Code Exchange) was previously required only for public clients (SPAs, mobile apps). RFC 9700 extends this requirement to server-side confidential clients too.

What PKCE prevents: authorization code interception. Even if an attacker captures your OAuth code in transit, without the `code_verifier` that only your app holds, the code is useless.

**What you should do today:**
→ Audit any OAuth integrations in production for Implicit Grant usage
→ Ensure all authorization code flows include PKCE
→ Update your authorization server library (most major ones already support RFC 9700)

This isn't optional. Major identity providers (Google, Microsoft, Auth0) are beginning to enforce these requirements at the provider level.

If auth is a core part of your product, read RFC 9700. It's a 25-page document that could prevent a serious breach.

Are your OAuth flows PKCE-compliant?

## Day 21 — The Discovery Call Framework That's Never Led Me to a Misaligned Project

**Format:** How-to / Process Share

**Post:**

A discovery call isn't a sales call.

It's due diligence — for both sides.

After 7 years of working with clients across three continents, I've structured every discovery call around six questions. The answers tell me almost everything I need to know:

**1. "What problem does this solve — and for whom, specifically?"**
Vague answer = unvalidated idea. Specific answer = they've done the work.

**2. "What does your user do today instead of using your product?"**
This reveals the real competitive landscape and how much behavior change you're asking users to make.

**3. "What does success look like in 90 days?"**
Forces a concrete outcome. "More users" is not success criteria. "100 paying subscribers at $49/month" is.

**4. "What's already been built or decided?"**
Existing designs, APIs, brand assets, or technical constraints I need to work within.

**5. "Who makes the final decision on this project?"**
If it's not the person on the call, you need to meet them before signing anything.

**6. "Why now?"**
The most revealing question of the call. A founder with urgency and a clear trigger is a completely different engagement than one who's been "thinking about this for two years."

I end every discovery call with: "Based on what you've shared, here's what I'd recommend we build first — and here's what I'd push to Phase 2."

That response alone tells both of us whether we're aligned.

## Day 22 — Your Error Monitoring Setup Is Probably Wrong. Here's How to Fix It.

**Format:** Technical How-to / Practical Guide

**Post:**

Every production app needs error monitoring.

Most setups I inherit are either incomplete or so noisy they've been muted by the team.

Here's what a genuinely useful error monitoring setup looks like:

**Tool: Sentry (my default for fullstack React/Node projects)**

**Step 1: Set up source maps properly.**
Without source maps, Sentry shows you minified stack traces. Unreadable. Useless. Set up source map uploads in your build pipeline — this is a 20-minute task that makes every future bug report 10× faster to debug.

**Step 2: Set meaningful alert thresholds — not "alert on every error."**
Alert fatigue is real. Configure your alerts to fire on:
→ New error types (not repeated instances of a known issue)
→ Error rate spikes (>5% of requests failing in a 5-minute window)
→ Performance regressions (p95 response time crosses a threshold)

**Step 3: Tag errors with user context.**
Sentry can capture the user ID, email, and session data with every error. This turns "something broke" into "this broke for 3 specific users — here's exactly what they were doing."

**Step 4: Monitor performance, not just errors.**
Set up Sentry Performance to track your slowest API routes, largest page components, and p75/p95 load times. Catch regressions before users report them.

Done right, error monitoring is not a chore. It's a real-time window into how your product is actually performing in the wild.

## Day 28 — The 3 Non-Negotiable Technical Foundations Every SaaS Needs Before It Launches

**Format:** How-to / Checklist

I've helped launch a lot of SaaS products.

The ones that scale without drama have three technical foundations locked in from day one. The ones that struggle have almost always skipped at least one.

**Foundation 1: Auth done right**
Not just "users can log in." Multi-provider support (email + Google at minimum). Role-based access control from the start. Refresh token rotation. Rate limiting on auth endpoints.

The moment you ship a SaaS product, someone will try to break your auth. Build it like they're already trying.

**Foundation 2: Observability from launch day**
Error monitoring (Sentry), structured logging with levels (not console.log), and at least one uptime monitor watching your critical user flows. You cannot improve what you cannot see. Don't wait for users to report bugs — know about them before users do.

**Foundation 3: A backup and recovery plan that's been tested**
An untested backup is not a backup. It's a hope. Know your data backup frequency, know your recovery time objective, and run a test restore before your first paying customer signs up.

Not glamorous. Not the features that make the demo impressive.

But the three things that separate "this product is reliable and trustworthy" from "we had an incident and it shook user confidence."

Get these right first. Then build features.
